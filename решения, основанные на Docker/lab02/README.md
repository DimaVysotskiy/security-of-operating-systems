# Лабораторная работа № 2. Управление локальными учётными записями

Цель — проверить сложность и срок действия паролей, блокировку после ошибок входа, смену пароля и удаление локальной учётной записи. Номера заданий соответствуют [исходной методичке](<../../исходники (Прокушев, Я.Е. Информационная безопасность операционных систем Linux : практикум по защите информации)/исходники отцифрованные в md формат/lab-02.md>).

## Предусловия

Часть действий исходной методички выполняется при сборке стенда. Ниже указано, что уже подготовлено к первому входу на каждую станцию. Сопоставление с исходными шагами приведено в [diff.md](diff.md).

### 1. Базовая система и пакеты на обеих станциях

[Dockerfile для `wrk1`](wkr1/Dockerfile) и [Dockerfile для `wrk2`](wkr2/Dockerfile) используют `alt:p11`. При сборке APT скачивает индексы штатных репозиториев ALT Linux p11 и устанавливает `login`, `passwd`, `pam`, `pam0_tcb`, `pam0_passwdqc` и `shadow-change`. После установки скачанные архивы и индексы удаляются. Оба Dockerfile копируют шаблоны из [policy/](policy/) и скрипт [configure.sh](configure.sh) в `/usr/local/share/lab02`.

### 2. Политика сложности паролей на `wrk1` (задание 3.1)

При сборке `wrk1` скрипт подготовки устанавливает [passwdqc.conf](policy/passwdqc.conf) в `/etc/passwdqc.conf`. Минимальная длина задаётся списком `24,24,24,12,8`, максимальная — 72 символа. Парольные фразы и генерация паролей модулем отключены. Параметры `match=4` и `similar=deny` участвуют в проверке сходства со старым паролем. Политика действует и при смене пароля от имени администратора. На выбор нового пароля отводится три попытки.

### 3. Срок действия паролей и очистка счётчика на `wrk1` (задание 3.2)

Скрипт копирует полный [login.defs](policy/login.defs) из образа `alt:p11` для `linux/amd64` с учебными значениями в `/etc/login.defs` с правами `0640`. При создании пользователя назначаются 91 день максимального срока действия, 0 дней между сменами и предупреждение за 10 дней до истечения срока.

Параметр `USERDEL_CMD` указывает на `/usr/local/sbin/lab02-clear-failures`. При удалении одной из учётных записей `user1`–`user4` этот скрипт удаляет её запись о неудачных входах из `/var/run/faillock`.

### 4. Блокировка после ошибок входа на `wrk1` (задание 3.3)

Шаблон [faillock.conf](policy/faillock.conf) устанавливается в `/etc/security/faillock.conf`. Четыре ошибки за 900 секунд приводят к временной блокировке на 60 секунд. Для хранения счётчиков скрипт создаёт каталог `/var/run/faillock`. Эти значения выбраны для стенда, поскольку в доступной копии задания отсутствуют страницы 64–65.

### 5. Локальный стек PAM на `wrk1` (задание 3.4)

Если в образе есть исходный `/etc/pam.d/system-auth-local-only`, скрипт сохраняет его как `system-auth-local-only.original` перед установкой учебного файла. Затем он устанавливает конфигурации `/etc/pam.d/login` и `/etc/pam.d/passwd`. Сервис `login` подключает все четыре части локального стека. Сервис `passwd` подключает часть `password`. За проверку пароля отвечает `pam_tcb`, за учёт ошибок входа — `pam_faillock`, за проверку нового пароля — `pam_passwdqc`.

### 6. Учётные записи на `wrk1` (задание 3.5)

Скрипт создаёт дополнительную группу `users`, если она отсутствует. После применения политик Dockerfile создаёт `user1` (Иван Иванов), `user2` (Мария Кузнецова), `user3` (Николай Николаев) и `user4` (Сергей Сергеев). У каждой учётной записи есть одноимённая основная группа, членство в `users`, домашний каталог и оболочка Bash. Пароли студент задаёт интерактивно.

### 7. Запуск станций и состояние `wrk2` (задания 3.10–3.11)

[Compose](../compose.yaml) запускает сервисы `lab02` и `lab02-wrk2` с именами хостов `wrk1` и `wrk2`. На обеих станциях включён `init`, а команда `sleep infinity` удерживает контейнеры запущенными между сеансами. На `wrk2` к первому входу доступны пакеты, шаблоны и скрипт подготовки. Студент сам запускает скрипт и создаёт учебные учётные записи в заданиях 3.10–3.11.

## Запуск стенда

Выполните на хосте из каталога с `compose.yaml`:

```bash
docker compose up -d --build lab02 lab02-wrk2
docker compose exec lab02 bash
```

## Практические задания

Административные команды выполняйте от `root` внутри `wrk1`, если в задании не указано другое место запуска. Используйте учебные пароли и исключите их из отчёта.

Оболочку `root` оставьте открытой для административных команд. Для проверки PAM из другого терминала на хосте запускайте `docker compose exec lab02 login user1`, подставляя нужного пользователя. После `exit` из учебной сессии вы вернётесь на хост. Команда `exec --user` запускает процесс с указанным UID без проверки пароля, поэтому для этого задания не подходит.

### 3.1. Проверьте настройки сложности пароля

```bash
cat /etc/passwdqc.conf
```

Найдите `min=24,24,24,12,8`: для паролей из трёх классов требуется не менее 12 символов, из четырёх — не менее 8. `passphrase=0` отключает специальную проверку парольных фраз, `enforce=everyone` применяет требования даже при смене пароля администратором. Найдите также параметры максимальной длины, сравнения со старым паролем и числа попыток выбора нового пароля.

### 3.2. Проверьте политику срока действия

```bash
grep -E '^(PASS_MAX_DAYS|PASS_MIN_DAYS|PASS_WARN_AGE|USERDEL_CMD)[[:space:]]' /etc/login.defs
chage -l user1
```

Сверьте значения из `/etc/login.defs` со сроками, которые показывает `chage -l user1`. Для изменения сроков существующей учётной записи используется `chage`.

### 3.3. Найдите параметры блокировки

```bash
cat /etc/security/faillock.conf
```

Найдите порог `deny`, окно подсчёта ошибок `fail_interval` и время разблокировки `unlock_time`. Параметр `retry` из задания 3.1 относится к выбору нового пароля.

### 3.4. Изучите локальный стек PAM

```bash
cat /etc/pam.d/system-auth-local-only
cat /etc/pam.d/login /etc/pam.d/passwd
```

Найдите типы `auth`, `account`, `password` и `session`. Проследите, какие части стека подключают сервисы `login` и `passwd` и где вызываются модули `pam_faillock` и `pam_passwdqc`.

### 3.5. Проверьте учётные записи и задайте пароли

```bash
grep -E '^user[1-4]:' /etc/passwd
ls -ld /home/user{1,2,3,4}
passwd user1
```

Сначала попробуйте ввести слабый учебный пароль, например шесть цифр. Зафиксируйте причину отказа. Затем задайте стойкий учебный пароль: удобно использовать сгенерированную строку от 16 символов с буквами обоих регистров, цифрами и знаками. Задайте отдельные пароли остальным пользователям:

```bash
passwd user2
passwd user3
passwd user4
chage -l user4
chage -d 0 user4
chage -l user4
```

Сравните вывод для `user4` до и после `chage -d 0`: теперь пароль нужно сменить при следующем входе. В записи `/etc/passwd` поле `x` является заполнителем, а не хешем пароля.

### 3.6. Проверьте блокировку и обязательную смену пароля

1. Запустите на хосте `docker compose exec lab02 login user1` и введите неверный пароль четыре раза. Если появится приглашение `login:`, снова укажите `user1`. Если команда завершится раньше, запустите её снова. До истечения 60 секунд попробуйте войти как `user1`. При блокировке PAM может вывести сообщение ещё до запроса пароля. Посмотрите счётчик в отдельной оболочке `root`:

   ```bash
   faillock --user user1
   ```

   После истечения блокировки повторите вход с верным паролем. Для продолжения работы без ожидания можно снять блокировку вручную: `faillock --user user1 --reset`.

2. Запустите на хосте `docker compose exec lab02 login user4` и введите установленный пароль. PAM должен потребовать смену. Сначала попробуйте вариант, отличающийся только одним символом, затем новый сильный пароль, существенно отличающийся от старого. Зафиксируйте реакцию в обоих случаях.

3. Выйдите из сеанса `user4` командой `exit` и в оболочке `root` выполните `chage -l user4`. Проверьте, что обязательная смена больше не требуется.

### 3.7. Удалите учётную запись

Убедитесь, что сеанс `user4` завершён. От `root` выполните:

```bash
userdel --help
ls -ld /home/user4
userdel -r user4
grep '^user4:' /etc/passwd
test ! -e /home/user4 && echo "Домашний каталог удалён"
```

После удаления `grep` не должен вывести запись. Ключ `-r` удаляет домашний каталог и почтовый ящик; файлы в других каталогах могут остаться.

### 3.8. Смените пароль от имени пользователя

Выполните на хосте:

```bash
docker compose exec lab02 login user1
```

После входа выполните `id`. Команда `passwd root` должна отказать в смене чужого пароля. Затем вызовите `passwd` без аргументов, введите текущий пароль и задайте новый. Завершите сеанс командой `exit` и убедитесь, что вход с новым паролем успешен.

### 3.9. Воссоздайте учётную запись

От `root` создайте `user4` заново, назначьте пароль и проверьте запись, домашний каталог и срок действия:

```bash
useradd -U -m -s /bin/bash -G users -c 'Сергей Сергеев' user4
passwd user4
id user4
ls -ld /home/user4
chage -l user4
```

### 3.10. Примените политики на `wrk2`

Вторая станция уже работает. Откройте её оболочку в отдельном терминале из каталога с `compose.yaml`:

```bash
docker compose exec lab02-wrk2 bash
```

Посмотрите шаблоны в `/usr/local/share/lab02`, примените настройки командой `bash /usr/local/share/lab02/configure.sh` и сверьте значения по заданиям 3.1–3.4.

### 3.11. Создайте учётные записи на `wrk2`

Создайте `user1`–`user4` через `useradd` по образцу задания 3.9. Задайте им те же учебные пароли, что действуют на `wrk1`, и проверьте вход с хоста командой `docker compose exec lab02-wrk2 login user1`.
